# Document-Oriented Model (Phase II-B)

**Project:** Large-Scale NYC Taxi Analytics  
**Database:** MongoDB (`nyc_taxi_analytics`)  
**Responsibility:** Member 2 — Document Design and MongoDB Ingestion  
**Dataset:** Same 12 Yellow Taxi Parquet files (2025, 48,722,602 records) loaded into PostgreSQL in Phase I

---

## 1. Design Goals

The relational schema from Phase I is normalized to 3NF: `taxi_trips` holds
the facts and four lookup tables (`vendors`, `payment_types`, `rate_codes`,
`taxi_zones`) hold descriptions. Most analytical SQL queries therefore need
at least one join.

The document model is designed around how the data is **read**, not copied
table-for-table:

1. Data that is always read together with a trip is **embedded** in the trip.
2. Data that is shared, larger, or useful on its own stays in a **separate
   reference collection** and is joined with `$lookup` when needed.
3. One **derived summary collection** uses arrays to store pre-grouped data
   that has a natural one-to-many shape.

## 2. Collections

| Collection | Documents | One document = | Source |
|---|---:|---|---|
| `trips` | 48,722,602 | one taxi trip | Parquet trip records |
| `taxi_zones` | 265 | one TLC taxi zone | `taxi_zone_lookup.csv` |
| `zone_summary` | 262 | one pickup zone with hourly statistics | derived from `trips` |
| `import_history` | 12 | one imported Parquet file | loader metadata |

### 2.1 `trips`

```json
{
  "_id": ObjectId("6af9f3c24653e08015bdfe33"),
  "source_month": "2025-01",
  "vendor":    { "id": 1, "description": "Creative Mobile Technologies" },
  "pickup":    { "datetime": ISODate("2025-01-01T00:18:38Z"), "location_id": 229 },
  "dropoff":   { "datetime": ISODate("2025-01-01T00:26:59Z"), "location_id": 237 },
  "passenger_count": 1,
  "trip_distance": 1.6,
  "rate_code": { "id": 1, "description": "Standard rate" },
  "store_and_fwd_flag": "N",
  "payment":   { "type_id": 1, "method": "Credit card" },
  "fare": {
    "fare_amount": 10.0, "extra": 3.5, "mta_tax": 0.5,
    "tip_amount": 3.0, "tolls_amount": 0.0,
    "improvement_surcharge": 1.0, "congestion_surcharge": 2.5,
    "airport_fee": 0.0, "cbd_congestion_fee": 0.0,
    "total_amount": 18.0
  }
}
```

**How it differs from the relational design:**

| Relational (Phase I) | Document (Phase II-B) | Reason |
|---|---|---|
| 20 flat columns in `taxi_trips` | Fields grouped into `pickup`, `dropoff`, `fare`, `payment`, `vendor`, `rate_code` subdocuments | Groups related fields; a query can project a whole subdocument (e.g. `fare`) at once |
| `vendor_id` → join `vendors` | `vendor: {id, description}` embedded | Only 4 vendors, values never change, always shown with the trip |
| `payment_type_id` → join `payment_types` | `payment: {type_id, method}` embedded | Query 5 (payment and tips) needs no join in MongoDB |
| `rate_code_id` → join `rate_codes` | `rate_code: {id, description}` embedded | Same as above |
| `pickup_location_id` → join `taxi_zones` | Only `location_id` stored; zone names stay in `taxi_zones` | 265 zones, used twice per trip (pickup and dropoff), and useful on their own. Kept separate to show `$lookup` and avoid repeating zone names 97 million times |
| NULL values stored | Missing values **omitted** from the document | MongoDB convention; saves space. `$avg` and `$sum` ignore missing fields the same way SQL `AVG`/`SUM` ignore NULL, so results stay comparable |
| `trip_id` identity column | `_id` ObjectId generated by MongoDB | Source data has no natural key in either system |

**Deliberate denormalization.** Embedding vendor, payment and rate code
descriptions repeats a short string in every trip. This breaks 3NF on
purpose: the descriptions are tiny, never updated, and removing the join
makes reads cheaper. Update anomalies are not a practical risk because the
TLC code tables are fixed.

**Embedding vs. referencing for zones.** Zones are referenced rather than
embedded because each trip touches two zones, zone names are long strings,
and zone-level analysis (zone summaries, zone-to-zone demand) treats the
zone as an entity of its own.

**`source_month`** records which Parquet file a document came from. It is
derived from the file name, used to verify per-file counts, and lets the
loader safely re-run one month after a failure.

### 2.2 `taxi_zones`

```json
{ "_id": 132, "borough": "Queens", "zone": "JFK Airport", "service_zone": "Airports" }
```

The TLC `LocationID` is used directly as `_id`, so `$lookup` from
`trips.pickup.location_id` or `trips.dropoff.location_id` uses the
built-in `_id` index.

### 2.3 `zone_summary` (array field)

```json
{
  "_id": 237,
  "zone": "Upper East Side South",
  "borough": "Manhattan",
  "total_trips": 2125560,
  "hours_with_pickups": 24,
  "hourly_stats": [
    { "hour": 0, "trips": 24129, "avg_distance": 7.22,
      "avg_total_amount": 20.39, "avg_duration_min": 11.62 },
    { "hour": 1, "trips": 11016, "avg_distance": 2.47,
      "avg_total_amount": 19.98, "avg_duration_min": 11.25 },
    "... 22 more entries, one per hour ...",
    { "hour": 17, "trips": 164522, "avg_distance": 2.93,
      "avg_total_amount": 22.08, "avg_duration_min": 13.52 }
  ]
}
```

Upper East Side South is the busiest pickup zone in 2025 (2,125,560 trips).
262 of the 265 taxi zones had at least one 2025 pickup.

- One document per pickup zone, built by `scripts/build_zone_summary.py`
  with an aggregation over `trips` (2025 pickups only, same date filter as
  the SQL queries).
- `hourly_stats` is an array with **one entry per hour of day that had at
  least one pickup** in that zone (up to 24). Zones with no pickups in some
  hours have fewer entries; `hours_with_pickups` records the array length.
- Every value is computed from source fields (`pickup.datetime`,
  `trip_distance`, `fare.total_amount`, pickup/dropoff times). No source
  fields are invented.
- This shape is natural for documents (a zone *has* 24 hourly profiles) and
  awkward in SQL, where it would need a separate `zone_hourly_stats` table.
  Phase III-A uses it for array operations (`$unwind`, `$filter`,
  `$arrayElemAt`).

### 2.4 `import_history`

Mirrors the PostgreSQL `import_history` table: one document per Parquet
file with expected rows, imported rows, duration and status. The loader
skips files already marked `success`.

## 3. Relational vs. Document Model Comparison

Both models hold the same 48,722,602 trips. They differ in how the data is
organized, which changes what is easy, what is fast, and what it costs.

| Aspect | Relational (PostgreSQL) | Document (MongoDB) |
|---|---|---|
| **Structure** | 1 fact table (`taxi_trips`, 20 flat columns) + 4 lookup tables | `trips` with nested sub-documents + `taxi_zones` reference + derived `zone_summary` |
| **Normalization** | 3NF: every description stored once | Deliberately denormalized: vendor, payment and rate code descriptions repeated in every trip |
| **Joins** | Needed to show any description (payment method, vendor, rate code, zone) | Only for zone names (`$lookup` into `taxi_zones`); all other descriptions are already in the trip |
| **Schema** | Fixed: every row has every column, NULL when unknown | Flexible: missing values are simply left out (e.g. `passenger_count` absent in 18.4% of sampled trips) |
| **One-to-many data** | Needs another table (e.g. a `zone_hourly_stats` table with one row per zone per hour) | Stored as an array inside one document (`zone_summary.hourly_stats`, up to 24 entries) |
| **Data integrity** | Foreign keys enforce valid codes; updates happen in one place | No foreign keys; a changed description would need updating in millions of documents |
| **Storage** | Column names stored once in the table definition | Field names repeated in every document: 28.1 GB uncompressed BSON (577 bytes/trip), 4.4 GB on disk after compression |
| **Bulk load** | `COPY` from CSV batches: ~18,200–19,600 rows/s, about 42 minutes for the year | `insert_many` batches: ~36,000–41,000 rows/s, about 20 minutes for the year |
| **Best suited for** | Ad-hoc queries across many relationships; data that changes; strict consistency | Read-heavy analytics where related data is read together; nested and array-shaped data |

**Notes on the numbers.**
- PostgreSQL load figures come from `postgres_load_2025-*.json` and MongoDB
  figures from `mongo_load_2025-*.json`.
- The two loads ran on **different computers** (PostgreSQL on a Mac,
  MongoDB on a Windows laptop) and use different loading methods, so load
  speed is only a rough indication, not a benchmark.
- PostgreSQL on-disk size for the same data: *to be added* (run
  `SELECT pg_size_pretty(pg_total_relation_size('taxi_trips'));`).
- A fair query-speed comparison, with both systems on the same machine and
  equivalent queries, is done in Phase III-B.

**Summary.** The relational model is cleaner and safer for updates because
each fact lives in one place. The document model trades some duplication
for fewer joins and a natural home for nested and array data, which fits
this dataset well: trip records never change after they are written, so
the usual downside of denormalization (update anomalies) does not apply.

## 4. Loading Process

`scripts/load_mongo.py`:

1. Loads `data/taxi_zone_lookup.csv` into `taxi_zones`.
2. Reads each `yellow_tripdata_2025-*.parquet` file in batches of 50,000
   rows with PyArrow (the same batch size as the PostgreSQL loader).
3. Converts each row into a trip document (`build_trip`) and inserts the
   batch with `insert_many(ordered=False)`.
4. Verifies inserted rows against the Parquet row count and the collection
   count increase, then records the file in `import_history`.
5. Saves per-file throughput to `results/mongo_load_YYYY-MM.json`.

Timestamps are stored exactly as in the Parquet files and PostgreSQL
(NYC local time, no time-zone conversion), so `$hour` in MongoDB returns
the same hour as `EXTRACT(HOUR ...)` in SQL.

## 5. Verification

`scripts/verify_mongo.py` wrote `results/mongo_verification.json`
(run 2026-11-15). Results:

| Check | Result |
|---|---|
| `trips` documents | 48,722,602 |
| Matches PostgreSQL / Parquet total | Yes (48,722,602) |
| `import_history` total | 48,722,602 (12 files, all `success`) |
| Per-month counts | Identical to the Parquet row counts in `dataset_inspection.md` |
| `taxi_zones` documents | 265 |
| `zone_summary` documents | 262 |
| Field types (100,000-document random sample) | All as expected: dates for timestamps, int for location and payment IDs, double for distance and amounts |
| `passenger_count` missing | 18.4% of the sample: these were NULL in the source data and were omitted, not stored as null |

**Storage.** The `trips` collection holds 28.1 GB of BSON data
(577 bytes per document on average) but uses only 4.4 GB on disk, because
MongoDB's WiredTiger engine compresses it. Field names are stored inside
every document, which is why the uncompressed size is larger than the
raw Parquet files.

**Data quality note.** The data was loaded raw, the same as in
PostgreSQL, so outliers from the source remain. For example, the
Upper East Side South summary shows an average trip distance of 49.93
miles at 5 AM, caused by a few trips with impossible recorded distances.
Phase III queries should filter outliers where it matters, the same way
in both systems.

## 6. Indexes

| Collection | Index | Purpose |
|---|---|---|
| `trips` | `_id` (default) | Primary key |
| `trips` | `source_month` | Loader verification and safe re-runs |
| `taxi_zones` | `_id` (= LocationID) | `$lookup` joins |
| `zone_summary` | `_id` (= LocationID) | Lookup by zone |

Query-specific indexes on `trips` (e.g. `pickup.datetime`,
`pickup.location_id`) are added in Phase III so they can be timed before
and after, matching the PostgreSQL indexing experiments.

## 7. How to Run

```bash
pip install pymongo pyarrow pandas
# MongoDB 4.4+ running on localhost:27017
python scripts/load_mongo.py          # ~48.7M trips + 265 zones
python scripts/build_zone_summary.py  # derived zone_summary collection
python scripts/verify_mongo.py        # counts, types, indexes, samples
```
